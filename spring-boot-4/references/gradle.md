# Gradle

Read this when creating a Gradle application or changing Gradle build files,
dependencies, plugins, tests, or packaging. For Maven, use [maven.md](maven.md).
Stack-specific dependencies remain in their matching references.

## When to use

- Create a new Gradle project
- Change `build.gradle`, `build.gradle.kts`, the Gradle Wrapper, or Gradle plugins
- Add dependencies or configure Gradle tests and packaging

## Rules

1. Use the committed Wrapper (`./gradlew` or `gradlew.bat`), not a machine's
   global Gradle installation.
2. Keep the DSL selected by the project or generated by Spring Initializr.
   For a new project, use the Boot version from `versions.json` under
   `springBoot.default`. Confirm the generated Spring Boot Gradle plugin uses
   that version and do not add `.RELEASE` to Gradle plugin or BOM versions.
3. Keep the Initializr `java` and `org.springframework.boot` plugins and its
   `io.spring.dependency-management` plugin. The latter imports the Boot BOM,
   so omit versions for Boot-managed dependencies. Do not add another Boot
   plugin or independently override Boot-managed versions.
4. Keep `mavenCentral()` or the repository already selected by the project.
   Gradle does not resolve dependencies until a repository is declared.
5. Put versions for third-party libraries in `gradle/libs.versions.toml` for a
   new project, or in the project's existing catalog or dependency constraints.
   Do not add a Maven `<dependencyManagement>` block. Copy pins from
   `versions.json`; Boot-managed dependencies do not need a catalog version.
6. Use Boot 4 starter names. Add the matching Boot `-test` starter for each
   production starter used by tests. Keep the Initializr context-load test,
   and configure the Gradle `test` task for JUnit Platform.
7. Keep Taikai test-scoped in new projects, using the version in `versions.json`.
   Add architecture rules for actual feature and dependency boundaries.
8. For JaCoCo, use Gradle's built-in `jacoco` plugin and generate reports from
   `check` or the requested verification task. Do not add a coverage threshold
   unless the user or repository policy defines one.
9. For a new Gradle project, apply `com.diffplug.spotless` using
   `spotless.gradlePlugin` from `versions.json` and configure Java with the
   same import cleanup and Palantir Java Format version used by Maven. Make
   `check` depend on `spotlessCheck`. Existing Gradle projects keep their
   formatter unless the task asks to align style.
10. Do not copy Maven plugin declarations or lifecycle phases into Gradle.
   Preserve existing Gradle plugins and task conventions; add equivalent
   tooling only when required by the project or task.

## Example

The Spring Initializr Groovy build uses this pattern. Keep the versions that
Initializr generated for the selected Boot line.

```groovy
plugins {
	id 'java'
	id 'org.springframework.boot' version 'BOOT_VERSION'
	id 'io.spring.dependency-management' version 'INITIALIZR_VERSION'
	id 'com.diffplug.spotless' version 'SPOTLESS_GRADLE_PLUGIN_VERSION'
}

group = 'com.example'
version = '0.0.1-SNAPSHOT'

java {
	toolchain {
		languageVersion = JavaLanguageVersion.of(21)
	}
}

repositories {
	mavenCentral()
}

dependencies {
	implementation 'org.springframework.boot:spring-boot-starter-webmvc'
	testImplementation 'org.springframework.boot:spring-boot-starter-webmvc-test'
	testImplementation libs.taikai
}

tasks.named('test') {
	useJUnitPlatform()
}

spotless {
	java {
		importOrder()
		removeUnusedImports()
		shortenFullyQualifiedTypes()
		expandWildcardImports()
		forbidWildcardImports()
		formatAnnotations()
		palantirJavaFormat('PALANTIR_JAVA_FORMAT_VERSION')
	}
}

tasks.named('check') {
	dependsOn tasks.named('spotlessCheck')
}
```

Read `spotless.gradlePlugin` and `spotless.palantirJavaFormat` from
`versions.json`. Use `./gradlew spotlessApply` to format and
`./gradlew spotlessCheck` to verify.

For third-party dependencies, define catalog aliases rather than repeating
versions in `build.gradle`:

```toml
# gradle/libs.versions.toml
[versions]
springdoc = "SPRINGDOC_VERSION"
therapi = "THERAPI_VERSION"
taikai = "TAIKAI_VERSION"

[libraries]
springdoc-openapi = { module = "org.springdoc:springdoc-openapi-starter-webmvc-ui", version.ref = "springdoc" }
therapi-runtime-javadoc = { module = "com.github.therapi:therapi-runtime-javadoc", version.ref = "therapi" }
therapi-scribe = { module = "com.github.therapi:therapi-runtime-javadoc-scribe", version.ref = "therapi" }
taikai = { module = "com.enofex:taikai", version.ref = "taikai" }
```

```groovy
dependencies {
	implementation libs.springdoc.openapi
	implementation libs.therapi.runtime.javadoc
	annotationProcessor libs.therapi.scribe
}
```

Use equivalent aliases in `build.gradle.kts`. Read
[openapi.md](openapi.md) for compatible springdoc selection, JavaDoc
descriptions, and development/production profile settings.

## Common tasks

```bash
./gradlew test       # run unit and integration tests
./gradlew check      # run verification tasks, including test and JaCoCo when configured
./gradlew bootJar    # build the executable archive
./gradlew bootRun    # run the application
```

## Verify

Read the Wrapper version, plugin versions, Java toolchain, repositories,
dependency declarations, and test task. For a new project, confirm the Boot
plugin version matches the selected Boot line, dependencies resolve from the
Boot BOM or version catalog, and `./gradlew check bootJar` succeeds. Report
any task that could not run because an external service was unavailable.
