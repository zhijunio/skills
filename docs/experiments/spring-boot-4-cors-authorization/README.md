# Spring Boot 4 技能对照：CORS 与资源授权

2026 年 11 月 24 日，两组代理分别为同一个已有写接口增加凭据式 CORS。基线服务使用 Spring Boot 4.2.0、Java 21、会话表单登录和默认 CSRF 保护。文档和偏好设置保存在内存中，供独立启动的实验实例使用。

## 实验设置

为了同时保留真实会话、资源归属和一个相邻接口，实验使用了专门准备的最小服务。两组从逐文件相同的基线独立开始，使用相同的模型、任务和运行环境。启用组可读归档的技能目录，共同验收留到实现之后才运行。 [任务原文](task.md) · [基线与技能快照](inputs.tar.gz)

任务要求仅向 `https://editor.example.test` 开放凭据式 `PATCH /api/documents/{id}`，预检须支持 `Content-Type` 和 `X-CSRF-TOKEN`。保留会话登录、资源归属、CSRF、相邻偏好设置接口及同源请求的原有契约。

## 共同验收方法

验收脚本用候选组的 Maven Wrapper 构建应用，在随机本地端口启动生成的 JAR，然后通过真实 HTTP 请求执行以下检查。

1. 无认证的允许来源预检返回精确来源、凭据许可、PATCH 和所需请求头。
2. 其他来源和方法，以及相邻接口和多余路径不获得新的跨源许可。
3. 所有者实际登录并带会话 Cookie 与有效 CSRF token，跨源写入成功并可读回。
4. 缺失或无效的 CSRF token 被拒绝。匿名请求即使有自己会话的有效 token 也不能写入。拒绝后原有数据不变。
5. 同角色非所有者收到原有的 `404`，目标资源不变。
6. 相邻接口保留同源写入与 CSRF 行为，文档接口也继续接受合法同源写入。

基线通过 Maven 构建。运行共同验收时，允许来源预检和允许来源实际响应的 CORS 许可检查按预期失败，其余四项通过。 [验收脚本](verify.sh) · [HTTP 测试代码](acceptance.py)

测试客户端使用 Cookie jar 管理真实服务端会话，并显式设置浏览器协议中的请求头。验证范围是服务端 HTTP 行为，浏览器实际部署中的 TLS、Cookie 分发和浏览器跨站策略需要在对应部署环境验证。

## 对照结果

| 检查 | 启用技能 | 未启用技能 |
| --- | --- | --- |
| 各组自行运行 Maven verify | 12 项通过 | 15 项通过 |
| 独立共同 HTTP 验收 | 6 项通过 | 6 项通过 |
| 生产代码改动 | 只改安全配置 | 只改安全配置 |

两组都在现有安全过滤链注册路径级 CORS 配置，指定精确来源、PATCH、两个请求头和凭据许可。原有的登录、授权、CSRF 和 Controller 保持原样。 [启用组改动](enabled.patch) · [未启用组改动](disabled.patch)

启用组在随机端口用 Java HTTP 客户端完成表单登录、Cookie 和 CSRF 流程。未启用组用完整 Spring 上下文的 MockMvc 驱动真实过滤链和表单登录，并独立检查相邻接口的同源 PATCH。未启用组在 Maven 验证后还启动了打包应用，手动检查真实会话的跨源写入。两组都覆盖了受限预检和非所有者写入。两组各自测试的参数化方式不同，数量用于复核运行结果。

两组首次自测都曾用固定的 `403` 判断受限预检。对于没有匹配到 CORS 配置的路径，服务可以返回 `200` 且省略许可头。两组都修正了断言，并通过最终验证。这提示技能里的 CORS 验收可以进一步明确：检查响应是否实际授予跨源许可，并在接口契约有要求时额外断言状态码。

每组只运行一次。本次两组都独立实现了同样的安全边界。观察到的差异主要是自行选择的测试入口。

## 复跑归档结果

准备 Java 21、Python 3、Maven 依赖缓存或仓库访问，以及 `rsync` 和 `patch`。在本报告目录执行：

```sh
work=$(mktemp -d)
tar -xzf inputs.tar.gz -C "$work"

for variant in enabled disabled; do
	cp -R "$work/base" "$work/$variant"
	patch -s -d "$work/$variant" -p1 < "$variant.patch"
	sh verify.sh "$work/$variant"
done
```

要重新实施对照，从归档的 `base/` 建两份相同独立副本，只给启用组归档中的 `skill/SKILL.md` 和相关参考。完成后对两份副本运行同一验收脚本。

## 后续复跑

同一任务又安排了两轮对照，启用组使用的技能只多了拒绝预检的断言规则。两份启用组的首次测试都检查 CORS 许可头。两份未启用组仍把拒绝预检断言为 `403`：第一份因此失败于实际返回的 `200`，第二份用自定义过滤器让应用返回 `403`，自身测试和 6 项共同 HTTP 验收都通过。第二份由另一个模型完成，不并入前三份的样本。记录和补丁在 [后续复跑](follow-up/README.md)。
