# 后续复跑：拒绝预检的断言

2026 年 11 月 24 日，在 [上一轮对照](../README.md) 之后，`security.md` 增加了一条规则：拒绝预检时检查 CORS 响应头是否授予许可，只有应用契约规定状态码时才断言具体状态。未匹配的凭据式预检可以返回 `200 OK`，同时没有 `Access-Control-Allow-Origin`。 [指引差异](security-guidance.patch)

复跑沿用同一基线和同一任务，计划做两轮独立对照。每轮一个启用组和一个未启用组。前三份提交在写出后中断。未启用组第二轮后来由当前会话的模型完成，前三份来自当时的另一模型，所以这一格不能并进前三份的样本。前三份的 Maven 与 HTTP 结果是在源码不再改动之后补跑的。

## 首次提交怎么判断拒绝预检

| 轮次 | 技能 | 拒绝预检的首次断言 | 首次 `./mvnw test` |
| --- | --- | --- | --- |
| 1 | 启用 | 响应没有 `Access-Control-Allow-Origin` | 11 项里 7 项通过。预检用例通过。4 项失败都在登录后的重定向断言 |
| 1 | 未启用 | 固定期望 `403` | 5 项里 4 项通过。拒绝预检失败：期望 `403`，实际 `200` |
| 2 | 启用 | 响应没有 `Access-Control-Allow-Origin` | 10 项全部通过 |
| 2 | 未启用 | 固定期望 `403`，并检查没有许可头 | 测试文件写出后第一次运行，14 项通过 |

启用组第一轮的失败断言期望登录响应的 `Location` 包含带端口的绝对地址，实际值是 `/`。 [启用组第一轮日志](logs/enabled1-first-verify.log) · [未启用组第一轮日志](logs/disabled1-first-verify.log) · [启用组第二轮日志](logs/enabled2-first-verify.log)

未启用组第二轮按记录要求先打包了当时的 `src`。那时还没有测试，第一次 `./mvnw test` 的输出是 `No tests to run`。 [这次空跑日志](logs/disabled2-first-verify.log) 随后写出的 `PortalCorsTests` 在第一次执行时就通过。拒绝文档预检的断言同时要求 `403 Forbidden`、响应体 `Invalid CORS request`，以及没有 `Access-Control-Allow-Origin`。相邻偏好接口的预检断言的是 `401`。

前三份生产代码都用安全过滤链上的路径级 CORS 配置。未启用组第二轮另外写了一个过滤器：跨源 `PATCH` 和对应预检交给 `DefaultCorsProcessor`，拒绝时直接结束过滤链，因此响应是 `403`。 [启用组第一轮](enabled1.patch) · [未启用组第一轮](disabled1.patch) · [启用组第二轮](enabled2.patch) · [未启用组第二轮](disabled2.patch)

## 共同 HTTP 验收

归档的 `verify.sh` 会先执行候选项目自己的测试。因此启用组第一轮和未启用组第一轮停在自己的测试失败，没有进入 HTTP 验收。跳过测试打包后，这两份安全配置通过了全部 6 项 HTTP 验收。启用组第二轮通过了包含自身测试在内的归档验收脚本，6 项 HTTP 检查通过。

| --- | --- | --- | --- |
| 1 | 启用 | 自身测试失败，未进入 HTTP | 6 项通过 |
| 1 | 未启用 | 自身测试失败，未进入 HTTP | 6 项通过 |
| 2 | 启用 | 6 项通过 | 不需要另跑 |

## 这次能说明什么

拿到新增规则的两份首次测试都用 CORS 许可头判断拒绝预检。没有拿到规则的第一份首次测试把拒绝预检写成固定的 `403`，并失败于实际返回的 `200`。没有拿到规则的第二份测试仍要求拒绝预检返回 `403`；它用自定义过滤器让应用返回这个状态，所以第一次运行测试就通过，共同 HTTP 验收也通过。共同验收只检查有没有跨源许可头。

前三份和第四份不是同一个模型。第四份因此不能补成前三份的对照格。现有结果仍然支持把这条规则留在技能里。样本量还不能单独证明它会稳定消除固定的 `403` 断言。
