# PostgreSQL Application Guidance

Use this reference for PostgreSQL datasource setup, SQL types, time-zone behavior, constraints,
indexes, or concurrent writes. It covers application integration, not server administration or
replication.

## Datasource

Use the PostgreSQL driver `org.postgresql:postgresql` with runtime scope. Let Spring Boot dependency
management select a compatible version. Check the actual server and JDBC driver independently; verify Instant mapping through the selected persistence provider (direct pgJDBC uses OffsetDateTime for timestamptz). When using MyBatis-Plus, do not add
`spring-boot-starter-jdbc` just to connect to PostgreSQL.

## Types and time zones

- Store instants as `timestamptz` and use `Instant` in Java. PostgreSQL stores the instant and
  renders it in the session time zone; it does not preserve the original zone identifier.
- Use `timestamp without time zone` for a wall-clock value only when the zone is intentionally
  outside the domain value.
- Keep application and database sessions in UTC. Configure server/database defaults and application
  connection settings so session behavior does not depend on the host's local time zone.
- Convert instants to a user's regional time zone at the presentation boundary. Preserve the API's
  existing timestamp serialization contract and test it at the HTTP boundary.

## Schema conventions

Use singular `snake_case` table names and `snake_case` columns. Name a column for the field, not the
table: prefer `status` in `purchase_order` over `purchase_order_status`. Keep Java properties in
`camelCase` and map differences explicitly. Quote reserved identifiers consistently in migrations,
queries, and persistence mappings; prefer lowercase identifiers for predictable PostgreSQL folding.

Name indexes `idx_<table>_<columns>`, unique constraints `uq_<table>_<columns>`, and foreign keys
`fk_<table>_<referenced_table>`. Add indexes for observed filters, joins, and ordering patterns;
primary keys and unique constraints already create indexes. PostgreSQL does not automatically
index referencing columns for foreign keys, so add those indexes when joins or parent deletes need
them.

Declare foreign keys for real ownership or referential-integrity rules and choose `ON DELETE`
behavior deliberately. Use database defaults for stable database-owned values. Keep defaults
consistent with nullability, such as `NOT NULL DEFAULT 0`. For audit timestamps, choose one source
of truth: application fill or a database default, not competing defaults.

## Constraints and concurrent writes

Use NOT NULL alongside CHECK when null is forbidden: a CHECK expression yielding NULL does not reject a row. UNIQUE permits multiple nulls by default; select NULLS NOT DISTINCT only when supported by the server and required by the invariant. For shared-schema tenancy, use tenant-qualified unique and foreign keys to prevent cross-tenant references. For lost updates choose a conditional update/version predicate, row lock or appropriate isolation based on the invariant; check affected row counts. Classify SQLSTATE and constraint names rather than retrying every database error. Handle serialization failures and deadlocks with bounded whole-transaction retries only for repeatable operations.

Let database constraints decide concurrent uniqueness. Do not use `SELECT` followed by `INSERT` as
a uniqueness check. Let the write encounter the unique constraint, roll back the failed transaction,
and map the conflict to a stable application response. Do not continue querying in a transaction
after a database write has failed.

Keep transactions short and limited to database work. Do not hold a transaction across email, HTTP,
or other remote calls. Retry only when the operation is safe to repeat, and retry the complete unit
in a fresh transaction rather than retrying a statement inside an aborted transaction.

Test constraints, optimistic-lock conflicts, and concurrent writes against PostgreSQL Testcontainers.
Mocks and H2 do not establish PostgreSQL behavior. Bound application concurrency against the
database connection pool; virtual threads do not increase PostgreSQL capacity.

Example migration fragment; it assumes an earlier migration creates `customer(id)`:

```sql
CREATE TABLE purchase_order (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL,
    external_id text NOT NULL,
    version integer NOT NULL DEFAULT 0,
    status text NOT NULL DEFAULT 'PENDING',
    created_at timestamptz NOT NULL,
    updated_at timestamptz NOT NULL,
    CONSTRAINT fk_purchase_order_customer
        FOREIGN KEY (customer_id) REFERENCES customer (id),
    CONSTRAINT uq_purchase_order_external_id UNIQUE (external_id)
);

CREATE INDEX idx_purchase_order_customer_id ON purchase_order (customer_id);
```

Choose identity generation only when it matches the application's ID strategy.

## Verify

Inspect the datasource properties, active profile, database/session time zone, migrations, and
persistence mappings affected by the change. Confirm the effective PostgreSQL session time zone is
UTC. Exercise database-specific constraints and concurrency against PostgreSQL; report anything
that cannot be verified from the project configuration or available test environment.
