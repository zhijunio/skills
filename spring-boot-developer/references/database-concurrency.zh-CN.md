# 数据库并发

并发请求可能读取相同状态并竞争更新。应根据不变量和竞争模式选择并发控制机制；内存中的 `synchronized` 无法协调多个应用实例。

## 唯一性优先使用数据库约束

唯一性和引用完整性应由数据库约束作为最终依据。先 `SELECT` 再 `INSERT` 会在两个请求并发时产生竞态。直接尝试写入，由唯一约束裁决，再将完整性异常转换为稳定的冲突响应。不要向客户端暴露原始 SQL 错误或约束名。

应在失败写事务之外（例如异常处理边界）转换异常。flush 时发生约束冲突后，持久化事务可能已经被标记为只能回滚；PostgreSQL 也会将当前事务置为失败状态，直到完成回滚。在 `@Transactional` 方法中捕获异常后继续执行查询，可能最终得到 `UnexpectedRollbackException` 或其他数据库错误。若 Service 捕获异常，应转换后重新抛出以触发回滚；不要继续当前工作单元。

## 乐观锁

对于会并发读写但并非持续高竞争的行，使用 `@Version`。更新时会带上读取到的版本；一个写入者成功，过期写入者会收到乐观锁异常。若客户端需要重新读取并决定下一步，将其映射为 HTTP 409。若 DTO 包含递增后的版本号，应在返回前 flush；参见[Spring Data JPA](spring-data-jpa.zh-CN.md)。

只有操作可安全重复，且每次重试都会开启新事务时才进行重试。不要在已标记回滚的事务中重试，也不要盲目重放包含外部副作用的命令。参见[弹性模式](resilience.zh-CN.md)和[事务](transactions.zh-CN.md)。

## 悲观锁

在等待比重复写入过期状态更合适的短临界区中，且确有高竞争时使用 `@Lock(PESSIMISTIC_WRITE)`。缩短事务，设置锁/语句超时；仅当有界重试安全时，才将死锁或锁超时视为暂时失败。锁会占用数据库能力，且代码以不一致顺序获取行时可能死锁。

悲观锁不能替代唯一约束，也不会保护未被查询/锁定的行。应针对目标数据库方言确认实际 SQL 和行为。

## 隔离级别与事务结构

除非已确认存在需要更强级别解决的异常，否则使用数据库默认隔离级别。竞争场景下 `SERIALIZABLE` 可能中止事务，并要求重试整个工作单元。事务应短且只包含数据库操作；不要在持锁期间调用 HTTP、发送邮件或等待用户操作。

设计多行不变量时，确保所有写入者遵循相同事务边界。JPQL/native 批量更新可能绕过实体回调和版本检查；应明确处理版本条件与递增逻辑，或在生命周期行为重要时加载并更新实体。

## 并发测试

使用生产同类型数据库进行集成测试。通过屏障让两个独立事务/线程同时尝试冲突操作，再断言不变量和胜出的操作。单线程 Repository 测试或 H2 测试不能证明 PostgreSQL 锁和约束行为正确。只有功能明确处理锁超时/死锁时，才增加对应场景。

## 常见问题

- 先检查是否存在再插入——由数据库唯一约束保证，并转换冲突异常。
- 在写事务中捕获 `DataIntegrityViolationException` 后继续执行——转换后重新抛出，或在事务回滚后映射；不要继续使用失败事务。
- 使用 Java 同步保护数据库行——无法跨实例协调；应使用约束或数据库锁。
- 在同一个事务中重试乐观锁异常——使用新事务重试整个操作。
- 获取悲观锁后再调用网络——持锁事务应短且只做数据库操作。
- 认为批量更新会执行实体回调和版本检查——显式处理，或改用实体更新。
- 只在 H2 或单线程下测试并发——应在生产同类型数据库中使用独立事务。

## 使用 Spring Boot 3.5.x 时

并发机制来自 JPA/数据库，基本保持不变。复制特定 Provider 的锁提示前，应核对项目管理的 Hibernate/Spring Data 版本以及目标方言生成的 SQL。
