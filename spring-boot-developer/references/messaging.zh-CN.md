# 消息

## 什么时候需要消息代理

当生产者与消费者需要独立扩缩容、异步处理、缓冲峰值或跨进程通信时，消息代理才值得引入。若只是同一应用中的简单调用，直接调用或应用内事件通常更清楚。引入 Broker 后要负责部署、Schema、重试、积压、监控和故障恢复。

## Kafka

### 生产消息

选择稳定的消息键以保证相关事件进入同一分区；发送失败应可观测，并按业务语义处理确认。不要假设发送调用返回就代表消费端已处理。

### 消费消息

消费者应支持重复投递，并在成功处理后提交 offset。处理并发、分区顺序、消费积压和失败重试时，要明确业务是否要求顺序保证。

### 序列化

定义明确、带版本的消息契约。避免直接发送 JPA 实体或语言内部对象；兼容性应通过 Schema 演进规则管理。消息中只包含消费者需要的数据。

### 错误与死信主题

对暂时性错误做有界重试；永久性错误应进入死信主题，保留足够上下文供排查与重放。死信主题需要监控和处理流程，不能成为无人查看的垃圾桶。

## RabbitMQ

明确 Exchange、Queue、Binding、确认机制、持久化和死信配置。消费者幂等与重试规则同样适用；避免无限 requeue 导致消息热循环。

## 消费者必须幂等

Broker 通常提供至少一次投递语义，因此相同消息可能被处理多次。通过业务唯一键、Inbox / 去重记录或幂等更新避免重复付款、重复创建等副作用。幂等边界要与事务边界一致。

## 事务 Outbox

数据库写入与消息发送无法靠普通本地事务原子完成。Outbox 模式在业务事务中同时写业务数据和待发布事件，再由独立发布器投递事件并标记完成。发布可能重复，因此消费者仍需幂等。跨服务一致性不能靠“先提交数据库再发消息”解决。

## 不要在未提交事务中直接发布

如果先发送消息、数据库事务后续回滚，消费者会看到不存在的数据；如果先提交数据库而消息发送失败，又会丢失事件。使用事务 Outbox，或在单进程内用事务提交后事件处理明确的可靠性边界。

## Schema 演进

采用向后兼容的增量演进：先让消费者兼容新旧字段，再发布生产者；删除或重命名字段需分阶段完成。给消息携带事件类型和版本，并保留历史消息可读取能力。

## 测试

测试序列化契约、重复投递、失败重试、死信路径、顺序要求和 Outbox 发布。需要验证 Broker 行为时使用 Testcontainers；不要只 Mock `KafkaTemplate` 就认为消息集成有效。

## 使用 Spring Boot 3.5.x 时

按 Boot 管理的 Kafka / RabbitMQ 依赖与自动配置使用。模块、属性和 Spring Batch / Modulith 集成可能随版本变化，应遵循目标 Boot 版本的配置。

## 常见问题

- 没有异步或解耦需求却引入 Broker。
- 假设消息只会投递一次，消费者不做幂等。
- 在业务事务未提交时直接发消息。
- 把实体对象直接序列化为消息契约。
- 无限重试或无限 requeue，导致积压和热循环。
- 有死信队列却没有监控、告警和处理流程。
- 消息 Schema 不兼容地改字段或删除旧字段。
- 只 Mock 消息发送器，不验证真实 Broker 行为。
