# MCP Server

本文讨论在 Spring Boot 中提供 Model Context Protocol（MCP）服务的主要设计点：传输方式、工具定义、错误边界、安全、客户端配置和测试。

## 传输方式

按部署形态选择传输。进程内由桌面客户端启动时通常使用 stdio；服务端部署、多个客户端连接时使用适合网络的 HTTP 传输。确认所用 Spring AI / MCP 版本提供的传输和生命周期配置，不要在业务代码中自行重做协议处理。

## stdio：保持标准输出干净

stdio 模式中，标准输出是协议通道，不能写启动 Banner、日志或调试信息。将日志发送到标准错误，并检查所有依赖库不会向 stdout 打印内容，否则 MCP 客户端会收到无效消息。

## 工具

### 工具描述就是给模型的提示

工具名称和描述会影响模型何时及如何调用。使用清楚、具体且边界明确的描述，说明参数含义、前置条件和副作用。不要用模糊描述，也不要把不可信用户输入拼进工具定义。

### 返回 DTO，并限制工具范围

工具应返回稳定的 DTO / 结构化结果，而非实体、内部异常或任意对象。限制结果大小、分页和执行时长；破坏性操作应要求明确参数和授权。一个工具只完成一项有边界的能力，避免暴露通用数据库或 Shell 执行入口。

## 错误

将可预期的业务失败转换为安全、可操作的工具结果；内部异常记录在服务端，不要把堆栈、凭据或内部拓扑返回给模型。区分可重试错误、无权限和参数无效。

## 安全

MCP 工具调用属于外部输入。每个工具都要执行认证、授权、输入校验、资源范围限制和速率 / 成本控制。不要因为调用来自模型就信任参数；模型输出与用户输入一样不可信。敏感写操作应审计，并且需要幂等保护。

## 客户端配置

客户端应明确配置传输、端点、认证和超时。秘密通过客户端或平台安全配置注入，不写入仓库。远程服务需要 TLS，并应限制可连接的主机与工具集合。

## 测试

测试工具 Schema、参数校验、成功结果、权限拒绝、业务错误、超时和 stdio 输出纯净性。对工具边界使用真实序列化与协议测试；不要只断言工具方法内部逻辑。

## 使用 Spring Boot 3.5.x 时

MCP 相关 API 由 Spring AI 版本决定，而非单独由 Boot 版本决定。确认 Boot、Spring AI、MCP Java SDK 的兼容组合，并使用对应版本文档中的传输配置。

## 常见问题

- stdio 模式把日志写到 stdout，破坏协议帧。
- 工具描述模糊或没有限制输入 / 输出规模。
- 向模型返回 JPA 实体、堆栈或内部错误细节。
- 把工具当成通用 SQL、文件系统或 Shell 入口。
- 信任模型提供的参数，不执行权限和输入校验。
- 无认证、超时、速率限制或审计。
- 未核对 Boot 与 Spring AI / MCP 版本兼容性。
