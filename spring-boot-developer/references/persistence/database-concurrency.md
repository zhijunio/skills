# Database Concurrency

Concurrent requests can read the same state and race to update it. Choose a concurrency control mechanism from the
invariant and contention pattern; an in-memory `synchronized` block does not coordinate multiple application instances.

## Prefer database constraints for uniqueness

For uniqueness and referential invariants, make the database constraint authoritative. A `SELECT`-then-`INSERT` check
races when two requests run together. Attempt the write, let the unique constraint decide, and translate the resulting
integrity exception into a stable conflict response. Do not expose raw SQL messages or constraint names to clients.

Translate the exception at a boundary outside the failed write transaction, such as an exception handler. After a
flush-time constraint violation, the persistence transaction may already be rollback-only; PostgreSQL also marks the
transaction failed until rollback. Catching the exception inside `@Transactional` and continuing with more queries can
end in `UnexpectedRollbackException` or another database error. If the service catches it, translate and rethrow so the
transaction rolls back; do not continue the unit of work.

## Optimistic locking

Use `@Version` for rows that are read and written concurrently but are not continuously contended. The update includes
the observed version; one writer succeeds and a stale writer receives an optimistic-lock exception. Map that to HTTP 409
when the client must reload and decide what to do. Flush before returning a DTO that includes the incremented version;
see [spring-data-jpa.md](spring-data-jpa.md).

Retry only when the operation is safe to repeat and a fresh transaction will be opened for each attempt. Never retry
inside a transaction already marked rollback-only, and do not blindly replay commands with external side effects.
See [resilience.md](../integration/resilience.md) and [transactions.md](transactions.md).

## Pessimistic locking

Use `@Lock(PESSIMISTIC_WRITE)` for a short, genuinely contended critical section where waiting is preferable to repeated
stale writes. Keep the transaction short, define lock/statement timeouts, and handle deadlocks or lock timeouts as
transient failures only when a bounded retry is safe. Locks consume database capacity and can deadlock when code
acquires rows in inconsistent order.

Pessimistic locking is not a substitute for a unique constraint, nor does it protect rows that were not selected/locked.
Verify the generated SQL and database behavior for the target dialect.

## Isolation and transaction shape

Use the database's default isolation unless a demonstrated anomaly requires a stronger level. `SERIALIZABLE` can abort
transactions under contention and requires retrying the whole unit of work. Keep transactions short and database-only;
do not hold locks across HTTP, email or user interaction.

Model multi-row invariants so every writer follows the same transaction boundary. A bulk JPQL/native update may bypass
entity callbacks and version checks; include version predicates and increment logic deliberately, or load and update
entities when lifecycle behavior matters.

## Concurrency tests

Use integration tests against the production database engine. Start two independent transactions/threads behind a
barrier, attempt the conflicting operation, then assert the invariant and expected winner/conflict. A single-threaded
repository test or H2 test cannot establish PostgreSQL lock and constraint behavior. Include a lock-timeout or deadlock
scenario only when the feature handles it explicitly.

## Gotchas

- Agent checks existence and then inserts - enforce uniqueness in the database and translate the conflict.
- Agent catches `DataIntegrityViolationException` inside a write transaction and continues - translate and rethrow, or
  map it after rollback; never continue using the failed transaction.
- Agent uses Java synchronization to protect a database row - it does not coordinate across instances; use a constraint
  or database lock.
- Agent retries an optimistic-lock exception in the same transaction - retry the whole operation with a fresh
  transaction.
- Agent takes a pessimistic lock and then makes a network call - keep the locked transaction short and database-only.
- Agent assumes bulk updates run entity callbacks and version checks - account for them explicitly or use entity
  updates.
- Agent tests concurrency only on H2 or in one thread - use independent transactions against the production database
  engine.

## If on Spring Boot 3.5.x

The concurrency mechanisms are JPA/database behavior and remain the same. Check the managed Hibernate/Spring Data
versions and SQL generated by the selected dialect rather than copying provider-specific lock hints across versions.
