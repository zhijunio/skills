# API 幂等性

幂等性确保同一个逻辑命令重试时不会产生重复效果。`PUT`、`DELETE` 等 HTTP 方法在协议语义上是幂等的，但应用仍需兑现该契约。对于创建支付或订单等非幂等操作，如果客户端可能因超时重试，应使用幂等键。

## 定义契约

明确哪些操作接受幂等键、由谁生成、作用范围、保留期限，以及重复请求如何响应。按认证租户/客户端和操作/路由限定键；一个租户的键绝不能重放另一租户的响应。要求客户端生成高熵值，限制长度，并拒绝格式错误或重复的 Header 字段。

业界 API 使用 `Idempotency-Key` Header，但 IETF 当前对应规范是已过期 Internet-Draft，并非 RFC。其语法和错误响应建议仍属暂定内容；宣称符合标准前应重新确认状态。应在 API 契约中定义实际采用的 Header 语法和重复请求行为。

## 原子化持久化结果

对于短小且只访问数据库的命令，在执行业务写入的同一事务中，保存由 `(tenant, operation, key)` 唯一约束保护的记录。记录请求的语义指纹、状态、生成的资源 ID、响应状态/正文或稳定结果引用，以及过期时间。只保存重放契约所需内容；响应可能包含敏感字段。

- 首次使用时保留该键并只执行一次操作。
- 相同键和相同请求返回原结果，不重复执行副作用。
- 相同键但请求不同，应拒绝重用。
- 并发重复请求应采用已文档化策略：等待并重放，或返回明确的处理中响应（常见选择为 409，或携带状态资源的 202）。

使用数据库唯一约束作为最终并发保护。不要采用“先查缓存再写数据库”。若并发插入违反唯一键约束，应回滚当前事务，再读取并处理已存在记录。记录保留期限应长于客户端重试窗口，并通过有界清理任务删除过期记录。

应对已校验的规范化命令生成指纹，而不是比较原始 JSON 字节；字段顺序或空格变化可能产生不同字节。唯一键还应包含认证范围和操作。重放已保存响应前重新检查授权。

## 外部副作用与长任务

不要在调用支付、邮件等远程服务时持有数据库事务。原子地保存命令结果和 Outbox 消息，再在事务外投递。下游服务支持时，传递稳定的下游幂等键；面对不确定的超时应进行对账，不要直接认定失败。参见[事务](transactions.zh-CN.md)、[消息](messaging.zh-CN.md)和[邮件](mail.zh-CN.md)。

长任务应持久化明确的 `PENDING` 状态，并使用可恢复的租约/尝试策略。异步处理时返回带状态资源 `Location` 的 `202 Accepted`。定义如何恢复废弃的待处理记录，以及何时允许重用键。

## 安全与测试

返回已保存结果前先完成认证和授权。幂等键不能充当授权凭据。保护存储的响应内容；若键可能关联敏感操作，应避免在日志中记录；并通过限流和保留策略限制无限增长。

集成测试覆盖首次成功、响应丢失后的重试、相同键不同请求、并发重复请求、事务回滚、键过期、租户隔离、下游超时对账，以及重放前权限发生变化的情况。唯一约束和竞态应在生产同类型数据库中测试。

## 常见问题

- 将 HTTP 幂等性等同于恰好执行一次——重试和远程超时仍需要持久状态与对账。
- 先查 Redis 再写数据库——并发请求可能同时通过；事务型命令应使用数据库唯一约束。
- 全局共享幂等键——纳入租户/客户端和操作范围，避免跨越安全边界。
- 重放前不重新检查授权——权限撤销后可能泄漏旧数据。
- 比较原始 JSON 字符串——应指纹化经校验的语义命令。
- 客户端仍会重试时键已过期——保留期应长于约定的重试窗口。
- 没有稳定下游键就重试远程副作用——提供方可能执行多次。
- 宣称 `Idempotency-Key` Header 已成为 RFC——先确认 IETF 文档状态；目前引用的草案已过期。

## 使用 Spring Boot 3.5.x 时

幂等性属于 API 和持久化设计，不是 Boot 专属功能。事务和数据库约束原则相同；仅需按项目 Boot 版本核对具体框架 API。
