# 数据库备份与恢复

只有能在服务恢复目标内还原所需数据的备份才有价值。选择备份频率和保留周期前，与服务负责人确定恢复点目标（RPO：可接受的数据丢失量）和恢复时间目标（RTO：可接受的恢复时长）。

## 设计恢复路径

根据 RPO/RTO 和数据库规模，选择数据库原生快照、持续归档/时间点恢复、逻辑导出或组合方案。备份副本应位于主故障域之外；平台支持时使用加密、最小权限和保留锁等控制。备份管理权限与应用凭据分离，并对备份遗漏、任务失败和保留策略偏差告警。

记录恢复顺序和依赖：创建隔离目标、恢复到指定时间点、加载必要配置和密钥、校验 Schema 与关键数据，最后仅在应用检查通过后切换流量。记录准确的命令或自动化、所需审批、预期时长和回退点。通过单独受控的紧急流程保存恢复凭据。

## 协调数据和应用状态

数据库备份可能不包含对象存储、上传文件、加密密钥、搜索索引或已发送到外部系统的消息。明确哪一处状态是权威数据，以及如何恢复或对账各个依赖。数据库和文件在不同时间备份可能造成引用断裂；应采用协调快照、不可变对象版本或明确的一致性/对账流程。

Schema 迁移不等于备份。删除或重写数据的迁移可能无法逆转，即使应用二进制可以回滚。优先使用 expand/contract，在破坏性步骤前建立恢复点，并确保恢复后的 Schema 可由兼容版本运行。参见 [Flyway](flyway.zh-CN.md) 和 [CI/CD 与发布](ci-cd-release.zh-CN.md)。

## 演练并验证

定期将备份恢复到隔离环境，使用生产数据库引擎和接近真实的数据量。测量实际 RPO/RTO，验证迁移和应用启动，通过关键记录数或校验和检查数据，并验证访问控制。备份任务成功不代表恢复有效。

恢复测试必须与生产集成隔离：禁用外发邮件、支付调用和定时任务，并使用独立凭据和端点。对恢复数据实施生产级访问控制；扩大测试使用范围前可能需要脱敏。记录演练结果、数据时间点、耗时、差距和整改负责人。

## 使用 Spring Boot 3.5.x 时

备份和恢复属于数据库/平台职责，不是 Boot 功能。继续使用 Boot 管理的迁移工具管理 Schema 演进，但应采用数据库提供方支持的备份和时间点恢复机制。针对生产所用的准确数据库引擎和版本验证恢复行为。

## 常见问题

- 把备份任务成功等同于可恢复：定期执行恢复和验证。
- 所有备份都存放在与数据库相同的账号或地域：隔离共同故障和凭据泄露风险。
- 使用不同数据库引擎测试恢复：生产特有的备份和迁移行为可能不同。
- 恢复生产数据后仍运行定时任务或外部集成：隔离目标并关闭副作用。
- 把 Schema 回滚当作数据恢复：破坏性数据变更需要恢复点和兼容的应用计划。
- 只备份数据库，遗漏文件或密钥：为每个权威数据存储定义一致性和恢复策略。
