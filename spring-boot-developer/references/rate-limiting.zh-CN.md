# 限流与资源保护

保护应用免受滥用流量和超过有限容量的合法突发流量影响。限流控制单位时间内的请求数；并发限制控制同时执行的工作量；配额限制累计用量。它们解决不同问题，可组合使用。Spring Framework 并发限制和重试参见[弹性模式](resilience.zh-CN.md)。

## 在合适的边界实施限制

使用 API Gateway 或边缘代理执行面向客户端/IP 的通用请求保护，在流量消耗应用资源前拦截。若限额按已认证用户、租户、套餐或操作计算，应在应用中实施业务限制。Gateway 规则无法单独保护领域配额或对象级授权。

按路由和主体选择策略：Token Bucket 允许突发并限制持续速率；固定/滑动窗口适用于简单配额；Semaphore/并发限制用于昂贵的在途工作。在 API 契约中定义窗口、突发额度、成本权重和重置行为。避免一个全局限额同时阻断健康探针、回调或所有租户。

只有正确配置受信任代理时，客户端 IP 才可信。不要接受不可信来源传入的任意 `Forwarded` / `X-Forwarded-For`。账户配额优先使用稳定的已认证身份；不要用原始 Token 或个人数据作为限流键。

## 同时保护资源维度

限流不能取代硬性资源上限。设置请求体和 multipart 限制、限制页面大小及查询复杂度、限制上传/存储配额、配置请求与依赖超时，并限制昂贵的并发任务。使用背压或 `429`/`503`，不要无限排队。限制执行器和连接池队列；虚拟线程不会增加数据库容量。

尽可能在解析请求体和调用昂贵 Service 前进行低成本拒绝。若请求已消耗大量请求体，或路由会绕过 MVC，不要只依赖 Servlet Interceptor。根据受保护资源，在 Gateway、Servlet Filter、Service 或存储层实施相应限制。

## 响应与分布式行为

客户端触发限流策略时返回 `429 Too Many Requests`；已知重置时间时提供有效的 `Retry-After`。错误正文使用 RFC 9457 `ProblemDetail`。[RFC 9333](https://www.rfc-editor.org/rfc/rfc9333.html) 标准化的 `RateLimit` 响应字段可传达策略和剩余配额；只暴露客户端可据此行动的值，近似限流器不要承诺精确重置时间。

进程内计数器按实例分别计数，且重启会清零。若策略必须跨副本成立，应使用共享限流存储或统一 Gateway。明确限流存储不可用时的行为：低风险读取可失败开放；高成本或容易被滥用的操作可失败关闭；也可采用保守的本地回退。限制对限流存储的调用，避免其故障导致整个应用故障。

## 可观测性与测试

记录允许/拒绝数量、限流存储延迟/错误、队列饱和和工作耗时。使用路由模板和策略名等低基数标签；不要将原始 ID、IP 或 Token 作为标签。若内部阈值会帮助绕过策略，就不要对外暴露。

测试拦截边界、状态/正文/Header、突发与补充行为、已认证租户隔离、可信代理解析、多实例行为和限流存储故障策略。算法测试使用可控时钟；至少通过一次连接真实共享存储的分布式集成测试。

## 常见问题

- 将 `@ConcurrencyLimit` 当成请求速率限制——并发限制和到达速率策略不同。
- 使用任意转发 IP Header 作为限流键——仅信任配置过的代理跳点传递的代理 Header。
- 用内存计数器实现多实例配额——每个副本都会各自计算限额。
- 增加限流却保留无上限请求体、页面、上传、队列或并发数——仍需设置硬资源上限。
- 将所有突发请求排队等待——队列应有界，并及时拒绝过载。
- 返回 429 却没有重试提示或结构化错误——定义重试行为并使用 `ProblemDetail`。
- 指标标签使用原始 IP 或账户 ID——采用路由模板和低基数策略标签。
- Redis 限流状态不可用时让所有读取失败——按路由定义故障策略。

## 使用 Spring Boot 3.5.x 时

HTTP 语义和资源上限与 Boot 版本无关。Spring Framework 的 `@ConcurrencyLimit` 是否可用取决于 Framework 版本线；参见[弹性模式](resilience.zh-CN.md)并遵循项目管理的 Framework 版本。限流通常由 Gateway 或专用限流器负责，不要假设 Boot 内置了通用限流注解。
