# 缓存一致性

本文说明数据库与缓存之间的一致性边界。Spring 缓存抽象、键、TTL、序列化和 Redis 配置参见[缓存](caching.zh-CN.md)。缓存是派生副本；除非架构明确指定其他数据源为事实来源，否则数据库仍是权威数据源。

## 选择一致性承诺

按数据集说明可接受的陈旧读取窗口。允许有界陈旧的缓存可将 TTL 作为兜底；授权、余额、库存预留等正确性关键决策应读取权威状态，或使用协调能力更强的设计。不要把 TTL 描述成即时一致。

默认采用 Cache-Aside：先读缓存，未命中时查数据库，再填充缓存。写入先更新数据库，并在提交后再失效或刷新缓存。缓存不可变 DTO 并显式指定键；参见[缓存](caching.zh-CN.md)。

## 失效与提交顺序

`@CacheEvict` 可能在外层数据库事务提交前执行。若提交失败，缓存只是被多余清空（通常会自我修复）。`@CachePut` 则可能发布随后被回滚的数据。普通 Cache-Aside 数据应在提交后失效，而不是发布尚未提交的值。

进程内的 `@TransactionalEventListener(AFTER_COMMIT)` 可以避免回滚时失效缓存，但不具备持久性：提交后进程崩溃可能导致事件丢失。若不能接受陈旧数据，或失效操作必须能跨崩溃恢复，应在数据库事务中写入 Outbox 记录，再由 Worker 失效/刷新缓存。数据库与 Redis 通常不共享原子事务；重复失效应保持幂等。

多实例部署时，失效操作必须传播到所有缓存实例。单实例本地缓存无法通过某一节点的失效保证全局一致。使用共享缓存或持久化/广播失效机制，并监控延迟和失败。

缓存键应包含所有影响可见性或表示形式的维度，例如租户、Locale 或授权范围。缓存命中不能绕过对象级授权。除非失效与撤权窗口明确且经过测试，否则不要缓存权限决策或高度敏感数据。

## 竞态与缓存击穿

失效过程中存在竞态：读者先读到旧数据库值，写者提交并清除缓存，随后读者又将旧值写回缓存。若不可接受，可使用带版本的缓存条目、比较并交换、可接受陈旧时间的短 TTL，或按键串行刷新。根据实际影响选择；分布式锁本身也会带来失败模式。

若通过 Outbox 驱动失效，应使用租约或数据库锁领取工作，避免多个 Worker 丢失或无限重复处理。事件应幂等，并保留足够的版本/代际信息，以拒绝较新写入之后到达的旧刷新。监控最老待处理失效的年龄；仅看队列长度无法判断键可能陈旧多久。

热门键同时失效时，应协调单个刷新任务，或采用有界的 Stale-While-Revalidate 策略。不要让所有请求同时穿透数据库。负缓存可保护高频未命中，但应使用短 TTL，并考虑新建资源是否需要立即可见。

## 故障策略

明确缓存不可用时的行为。对非关键读取，若连接池能承受，可回退到数据库；否则应快速失败或削减负载。不要让缓存故障静默触发无界数据库击穿。失效/刷新失败需要指标和日志，但不能记录敏感缓存内容。

## 测试

按需测试提交和回滚、多实例或所选失效传输、相关的陈旧读者竞态，以及缓存不可用时的回退。当序列化、TTL 或 Pub/Sub 行为属于一致性承诺时，至少用一次集成测试验证真实缓存实现。可使用 Testcontainers 提供 Redis；参见[Testcontainers](testcontainers.zh-CN.md)和[事务](transactions.zh-CN.md)。

## 常见问题

- 认为 `AFTER_COMMIT` 监听器具备持久性——失效必须跨进程崩溃恢复时使用 Outbox。
- 在数据库事务提交前更新缓存——回滚会让缓存保留从未提交的值。
- 清除缓存但忽略并发旧读者重新填充——若陈旧值复活违反要求，应选择竞态处理策略。
- 多实例服务使用本地缓存并认为各节点都能看到失效——使用共享存储或跨实例失效机制。
- 把 TTL 当作即时一致——说明并测试真实陈旧窗口。
- Redis 故障时让所有请求无界回退到数据库——限制回退负载并明确故障策略。
- 只用 Mock 测注解——真实序列化和失效属于承诺时，要验证实际边界。

## 使用 Spring Boot 3.5.x 时

事务与缓存的时序原则不变。Redis 序列化器类名在 Boot 3.5（Jackson 2）和 Boot 4（Jackson 3）之间不同；按实际版本线参阅[缓存](caching.zh-CN.md)和[版本与升级](boot-versions.zh-CN.md)。
