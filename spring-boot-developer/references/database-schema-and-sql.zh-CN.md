# 数据库 Schema 与 SQL

根据持久的业务不变量和应用需要支持的查询来设计关系型 Schema。明确处理数据库专属行为，并在生产同类数据库引擎上验证。本指南涵盖通用 Schema 和 SQL 决策；JPA 与 MyBatis-Plus 映射分别参阅对应持久化文档，[Flyway](flyway.zh-CN.md) 介绍迁移流程，[数据库并发](database-concurrency.zh-CN.md) 介绍并发写入和锁。

## 设计表和列

- 使用稳定且能表达含义的表名和列名。常见约定是复数 `snake_case` 表名和 `snake_case` 列名，Java 属性使用 `camelCase` 并映射到数据库列。领域需要或已有 Schema 要求时可以使用保留字，但必须按照目标数据库的标识符引用语法处理，并在 DDL、SQL 和 ORM 映射中保持一致（例如 PostgreSQL 使用 `"user"`，MySQL 通常使用 `` `user` ``）。避免使用没有领域含义的缩写，以及表达临时实现的名称。列名不要重复表名的含义：例如 `role` 表优先使用 `name`，而不是 `role_name`；join 导致列名有歧义时，在 SQL 中使用 `r.name` 这样的限定名。
- 根据访问模式和增长情况选择主键。标识符保持不可变。代理主键不能替代业务键上的唯一约束。选择时间有序 ID 时应考虑索引局部性和信息暴露；标识符永远不能作为授权判断。雪花 ID 无法保证跨节点或时钟偏差时仍全局单调递增，因此不要用 ID 顺序表示业务时间顺序；若顺序重要，应存储显式时间戳或序列。UUIDv7 和实体标识规则参见 [Spring Data JPA](spring-data-jpa.zh-CN.md)。
- 选择能够保留领域值及预期范围的最精确数据库类型。对货币以及需要精确运算的数量使用 `DECIMAL` / `NUMERIC` 等精确数值类型；浮点类型是近似值。应明确指定精度和小数位数。
- 根据含义表示时间点和本地日历值。以一致方式持久化事件时间（通常使用 UTC），并明确应用、JDBC 和数据库的时区假设。本地业务日期或本地墙上时钟时间不能与时间点互换。
- 有意确定可空性。`NOT NULL` 表示数据不变量；不要用 `NULL` 表示多个无关状态。如果状态有业务含义，应使用有定义的状态字段或单独关系。只有当数据库是该默认值的明确所有者时才设置默认值。
- 避免在一个列中混合多种含义，或将必须单独筛选、连接、约束或更新的数据序列化为 Blob。只有当数据本身确实是文档结构，并且已理解目标数据库的索引和校验行为时才使用 JSON。

## 使用数据库约束表达不变量

对于必须由所有写入方共同遵守的不变量，数据库是最终权威。这些写入方包括应用实例、任务、脚本和未来的服务：

- 使用 `PRIMARY KEY` 表示行标识。
- 使用 `NOT NULL` 表示必需值。
- 使用 `UNIQUE` 保证业务键不重复。
- 使用 `FOREIGN KEY` 保证被引用的行存在；应有意选择 `ON DELETE` 行为，不要依赖默认值。
- 当目标数据库能按预期执行表达式时，使用 `CHECK` 表达行内规则。

应用校验能提供友好的错误，但在并发写入下不能替代数据库约束。应在应用边界将约束冲突转换为稳定的领域错误或 HTTP 错误；不要向客户端暴露 SQL 文本或约束名。参见[数据库并发](database-concurrency.zh-CN.md)。

不同数据库对唯一约束、`NULL` 语义、排序规则、大小写敏感性和延迟约束的行为可能不同。明确预期行为，并在生产数据库上验证。如果软删除会改变唯一性，应结合恢复行为设计唯一键或数据库专属的部分 / 过滤索引；逻辑删除的边界参见 [MyBatis-Plus](mybatis-plus.zh-CN.md)。

## 根据查询形状设计索引

索引会增加写入、存储和维护成本。只有在服务真实查询或约束时才添加，然后验证目标数据库是否能使用它：

- 从有代表性的 `WHERE`、join 和 `ORDER BY` 条件入手。复合 B-tree 索引的列顺序很重要；根据查询形状和选择性安排列，并通过执行计划验证，不要将通用规则机械套用到所有查询。
- 对重要外键查找和 join 路径添加索引，前提是数据库不会自动创建。在 PostgreSQL 中，声明外键不会自动为引用列建索引。
- 分页排序中加入稳定的次级排序字段。匹配的复合索引可以支持 keyset 分页；参见 [Spring Data JPA](spring-data-jpa.zh-CN.md)。
- 不要默认给每一列单独建索引。检查现有复合索引是否已覆盖前导查询条件，并考虑索引会增加插入、更新和删除的成本。
- 使用有代表性的数据检查 `EXPLAIN` / `EXPLAIN ANALYZE` 输出。`EXPLAIN ANALYZE` 会执行语句；对写入语句和昂贵的生产查询应谨慎使用。保持统计信息具有代表性，并对照预期检查实际行数和耗时。数据库专属行为参见 PostgreSQL [Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html) 指南。

## 安全且有意识地编写 SQL

- 通过预编译参数或持久化框架的参数绑定 API 绑定所有值。绝不要把请求数据拼接进 SQL。参数只能绑定值，不能绑定标识符或关键字；应将公开排序 / 筛选名称映射到固定白名单中的列和方向。参见 OWASP [SQL 注入防护备忘单](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)。
- 将原始 SQL 片段、动态表名 / 列名和数据库专属表达式视为需要审查的代码。保持其内容固定，或从严格的服务端白名单中选择。
- 查询应用数据时显式列出需要的列，不要使用 `SELECT *`。这能使结果映射保持明确，并避免不必要地读取大字段或敏感字段。
- 当调用方需要稳定分页或可重复结果时，确保排序是确定的。不带完整 `ORDER BY` 的 `LIMIT` 无法确定返回哪些行。
- 让破坏性语句的影响范围清晰可见。更新或删除前检查谓词和预期影响行数；大规模变更应使用事务和操作上安全的批次大小。缺少谓词时不能静默地修改所有行。
- 当生命周期和并发影响已明确时，批量工作优先使用集合式 SQL。批量 JPQL / 原生 SQL 和 MyBatis 自定义 SQL 可能绕过实体回调、乐观锁版本检查或逻辑删除行为；应显式实现等价规则并测试。参见 [Spring Data JPA](spring-data-jpa.zh-CN.md)和 [MyBatis-Plus](mybatis-plus.zh-CN.md)。

## 限制查询成本并验证行为

集合 Endpoint 和内部扫描必须分页或明确限制结果大小。设置最大分页大小、使用确定性排序，并在深度顺序遍历时优先考虑 keyset 分页。限制 `IN` 列表、报表范围和批次大小，确保有效请求不会造成无界数据库负载。请求级资源保护参见[限流与资源保护](rate-limiting.zh-CN.md)。

使用生产同类数据库测试 DDL、约束、类型、生成 / 自定义 SQL、排序规则行为和查询结果。H2 兼容不能证明 PostgreSQL、MySQL 或其他数据库会有相同行为。可行时使用 Testcontainers；参见[持久化切片测试](testing-slices-persistence.zh-CN.md)和[Testcontainers](testcontainers.zh-CN.md)。测试数据应有足够代表性以暴露查询计划和索引问题；表很小时，顺序扫描往往就是正确计划。

## 安全演进 Schema

生产 Schema 变更应使用版本化迁移文件。不要把 ORM 启动 DDL 当作生产 Schema 变更流程。优先采用同时兼容当前部署版本和下一版本的增量变更；重命名、类型变更和删除应使用 expand-and-contract。若单个迁移事务会持有锁或造成不可接受的负载，应分批回填大表。迁移命名、顺序和发布细节参见 [Flyway](flyway.zh-CN.md)。

应用行为应放在应用层。不要引入自定义存储函数 / 存储过程、触发器、数据库扩展或其他数据库引擎专属的可编程对象：它们会将行为与数据库引擎耦合，并增加本地开发、迁移、回滚和测试的复杂度。优先使用应用代码和可移植 SQL。如果遗留 Schema 中已经存在此类对象，应记录引擎 / 版本依赖，通过版本化迁移管理其 DDL，并在对应数据库引擎上验证升级、回滚、备份和恢复流程。

## 使用 Spring Boot 3.5.x 时

本指南中的关系模型设计和 SQL 原则与 Boot 版本无关。Provider 行为、SQL 生成和 Java 映射支持取决于项目管理的 Spring Data / Hibernate / MyBatis 与 JDBC 驱动版本；应使用准确的生产数据库和依赖版本验证生成的 SQL。Boot 4 更改了部分持久化 starter 和库版本；参见 [Boot 版本](boot-versions.zh-CN.md)、[Spring Data JPA](spring-data-jpa.zh-CN.md)和 [MyBatis-Plus](mybatis-plus.zh-CN.md)。

## 常见误区

- 先用 `SELECT` 检查唯一性，再执行插入——应使用数据库唯一约束并转换冲突。
- 将 `NULL` 当作业务状态，却不定义其含义——应显式建模状态，并在目标数据库验证唯一约束和 `NULL` 行为。
- 添加索引时不参考查询形状——应检查实际执行计划并考虑写入成本。
- 假定外键会自动在引用列上创建索引——应确认目标数据库行为，并添加所需索引。
- 使用浮点类型表示精确货币——应使用合适的精确数值类型，并明确精度 / 小数位数。
- 将请求数据拼接到 SQL，或允许任意排序标识符——应绑定值并对白名单中的标识符进行选择。
- 期待没有完整排序条件的 `LIMIT` 返回稳定页面——应使用确定性排序和次级排序字段。
- 执行批量变更却不检查谓词或影响行数——应限制语句范围并验证变更行数符合预期。
- 只在 H2 上测试生产 SQL——应使用生产同类数据库测试。
- 通过 ORM 启动 DDL 修改 Schema——应使用版本化迁移和兼容发布策略。
- 引入自定义存储函数、触发器、数据库扩展或其他数据库引擎专属的可编程对象——应将行为放在应用层并使用可移植 SQL。
