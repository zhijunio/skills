# CI/CD 与安全发布

将 CI 视为从已审查提交到生产运行制品的可重复路径。明确构建、验证、打包和部署阶段；本地与 CI 使用相同的 Wrapper 和检查命令。项目命令索引参见 [Taskfile](taskfile.zh-CN.md)。

## 一次构建并验证制品

打包前运行格式化/静态检查、编译、单元与切片测试、依赖真实服务的集成测试、迁移校验以及依赖和安全扫描。凭据存放在 CI 秘密存储中，或使用联合工作负载身份。按平台策略锁定经过审查的 Action/插件版本和容器基础镜像版本或摘要。

从一个提交构建一个不可变 JAR 或镜像，附带提交和构建元数据，并将同一制品晋级到各环境。不要为预发布和生产分别重新构建。记录源提交、制品摘要、构建结果和部署环境，确保事故时能定位运行版本。供应链策略要求时生成 SBOM 和构建来源证明。

## 协调数据库结构与应用变更

先部署向后兼容的数据库变更，再部署依赖它的代码。采用 expand/contract：新增可空列、表或兼容索引；部署可兼容新旧结构的代码；分批回填并观测进度；切换读写逻辑；待旧版应用全部退出且恢复窗口结束后，再删除废弃结构。参见 [Flyway](flyway.zh-CN.md)。

应用回滚不会自动回滚数据库迁移。破坏性数据变更优先采用向前修复；不可逆变更前验证备份，并明确各数据库结构状态兼容哪些应用版本。

## 发布与恢复

根据服务容量和风险选择平台支持的滚动、金丝雀或蓝绿发布。流量切换前等待就绪状态正常；存活探针不应依赖远程服务。终止实例前先排空流量并允许优雅关闭。明确健康检查、冒烟请求和回滚条件。

金丝雀发布期间，将错误率、延迟分位数、资源饱和度和关键业务结果与稳定版本对比。达到预设阈值时停止晋级。只有当前数据库结构和外部副作用仍兼容时，才回滚到旧制品；否则执行向前修复。功能开关可以将代码部署与功能启用分开，但临时开关要指定负责人和移除日期。

## 流水线权限与环境

构建任务和部署任务使用分离且符合最小权限原则的身份。平台支持时使用短期生产凭据，并将权限限定在目标环境；不可信的 Pull Request 代码不应接触生产凭据。通过仓库评审和环境保护规则控制生产晋级，不要把长期生产凭据写进工作流文件。

测试数据和服务应相互隔离。CI 不要连接生产数据库、邮箱、对象存储桶或支付账户。部署配置应位于制品之外；发布前校验必需配置，诊断输出不得打印秘密。参见[配置](configuration.zh-CN.md)和[可观测性](observability.zh-CN.md)。

## 发布证据与测试

流水线应留下可检查的证据：源版本、测试和扫描结果、制品摘要、迁移结果、部署状态和回滚决定。使用打包后的制品执行启动冒烟检查；使用生产数据库引擎测试迁移路径。高风险发布应演练回滚和备份恢复，不能把部署成功当作可恢复性的证明。

## 使用 Spring Boot 3.5.x 时

这些发布实践与 Boot 版本无关。Java 运行时、Boot 插件/Parent、依赖 BOM 和容器镜像应与项目支持的 Boot 版本保持一致；使用 Boot 管理的版本，不要独立固定框架依赖。参见[版本与升级](boot-versions.zh-CN.md)。

## 常见问题

- 为每个环境重新构建制品：晋级通过验证的同一摘要。
- 先部署依赖新结构的代码：采用 expand/contract 顺序。
- 认为回滚 JAR 会回滚数据库：规划结构兼容和向前恢复路径。
- 不等待就绪状态或观察错误及业务信号就发布：设置流量切换和晋级门槛。
- 让 Pull Request 工作流读取生产秘密：使用受限身份和受保护环境。
- 未演练恢复就认为部署可恢复：实际演练备份恢复和回滚。
