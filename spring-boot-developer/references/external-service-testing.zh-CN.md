# 外部服务测试

根据测试要证明的结论选择边界。Mock 可以验证应用分支逻辑，但无法证明 HTTP 序列化、认证请求头、超时行为或与真实提供方的兼容性。使用本地替身覆盖确定性的失败场景，使用契约测试验证线上的接口约定。

## 在边界测试出站 HTTP 客户端

将 HTTP 客户端放在精简的应用端口后面。单元测试可以伪造该端口以验证领域决策。增加客户端边界测试，使用真实请求工厂和序列化逻辑连接本地 HTTP 服务，并断言方法、路径、请求头、请求体、响应映射、错误转换和超时行为。提供方响应样本应包含未知字段以及格式错误和错误状态。

测试需要控制 HTTP 响应和检查请求时，可使用 WireMock 或 MockWebServer 等本地 Stub Server。Stub 应保持确定性，绑定临时端口，在测试间重置映射和场景，不要让并行用例共享可变预期。不要 Mock Spring 内部的 `RestClient` 或 `WebClient` 调用链；应在网络边界验证行为。

## 本地开发与提供方契约

条件允许时，为本地开发的每个外部依赖提供有文档说明的替身或沙箱。替身行为应明确且安全：使用虚假凭据，拒绝意外调用，不发送真实邮件、支付或客户数据。Docker Compose 可以启动兼容的本地服务，但它不能证明与生产提供方兼容。

对关键集成，根据提供方的 OpenAPI/Schema 或消费者驱动契约维护接口契约。契约变化时验证客户端对请求和响应的假设仍成立。若双方都由本团队负责，则针对已发布的消费者契约运行提供方验证。契约测试应配合少量沙箱或受控端到端检查；它不能证明提供方的可用性或运维行为。

提供方支持时固定 API 版本。将提供方示例和录制夹具视为数据：移除秘密和个人信息，并在契约变化时有意更新。参见 [HTTP 客户端](http-clients.zh-CN.md)、[OpenAPI](openapi.zh-CN.md) 和[弹性模式](resilience.zh-CN.md)。

## 消息、邮件与对象存储

生产协议或引擎很重要时，使用 Testcontainers，例如消息代理、数据库或 S3 兼容对象存储。邮件渲染和投递流程使用本地邮件收件箱。对本地替身无法模拟的行为，保留少量提供方沙箱测试；若测试成本高或有状态，应与普通 CI 隔离或设为显式触发。

除成功外还要验证失败和恢复：超时、拒绝连接、4xx/5xx 映射、格式错误的响应、重复投递、重试上限、熔断状态和清理行为。避免依赖公网可用性或共享的真实凭据。

## 安全配置测试

为测试替身配置明确的基础 URL；测试 Profile 指向生产主机时应快速失败。替身缺失时，不要静默回退到真实端点。请求或响应可能包含 Token 和个人信息时，不要记录完整内容。如果并行测试共用一个替身，使用唯一 ID 隔离场景，并确保清理逻辑不会删除其他测试的数据。

## 使用 Spring Boot 3.5.x 时

边界测试原则相同。Boot 管理的客户端和测试 API 会随版本变化；遵循 [HTTP 客户端](http-clients.zh-CN.md) 及项目管理的测试依赖，不要把 Boot 4 代码片段直接复制到 3.5.x 项目。

## 常见问题

- Mock 客户端内部实现后便认为 HTTP 契约已验证：使用本地服务在网络边界测试。
- 缺少 Stub 时让测试 Profile 指向真实端点：应快速失败，不能静默访问生产。
- 把本地替身当作提供方兼容性的证明：对此结论增加契约或受控沙箱测试。
- 并行测试共享可变 Stub 场景：隔离状态并在测试间重置。
- 在夹具中记录真实 Token 或客户数据：清理夹具并使用虚假凭据。
- 只测试成功响应：覆盖超时、错误响应、状态映射、重试和重复副作用。
